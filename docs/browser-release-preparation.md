# Browser extension release preparation

This document covers **preparation only**: deterministic unsigned submission
ZIPs for the Locklark browser extension, the public metadata needed to review
them, and the native-host/store identity facts that a later release must keep
continuous. It does not sign, publish, upload, review, or install a release.

> **Unsigned preparation ZIP is not a signed store release.**
>
> `scripts/package_browser_extension.py` produces a ZIP containing the product
> files and generated manifest. A Chrome Web Store, Microsoft Edge Addons, or
> Firefox AMO release additionally requires the release owner's store account,
> listing/validation, review, and the store's signing or packaging step. This
> worktree performed none of those steps.

No support URL, privacy-policy URL, homepage URL, store listing text, or license
choice is created or implied by this preparation. Those are release-owner
decisions and must not be invented in the manifest or a store form.

## Prepared artifact

Run the packager with an explicit output directory. The parent directory must
already exist; the output directory itself is created if needed.

```sh
mkdir -p /absolute/release-parent
python3 scripts/package_browser_extension.py \
  --product chromium \
  --output /absolute/release-parent
python3 scripts/package_browser_extension.py \
  --product firefox \
  --output /absolute/release-parent
```

Each run invokes `node build.js <product>` in the resolved
`browser-extension` directory using an argv list, `shell=False`, no stdin, and
the existing `browser-extension/build.js`. The packager does not read profiles,
vaults, browser data, home-directory state, credentials, or environment
variables to choose inputs. The explicit allowlist is:

```text
manifest.json
core.js
content.js
webauthn.js
background.js
popup.html
popup.css
popup.js
options.html
options.css
options.js
```

Tests, source maps, hidden files, extra build output, directories, symlinks,
profile data, and vault data are not accepted. The built directory must contain
exactly those names; a symlink or non-regular file at any allowlisted path is a
hard failure. Normal output is:

```text
locklark-browser-extension-chromium-unsigned.zip
locklark-browser-extension-chromium-unsigned.receipt.json
locklark-browser-extension-firefox-unsigned.zip
locklark-browser-extension-firefox-unsigned.receipt.json
```

Both products may use the same output directory. Re-running into a directory is
allowed only when every existing file is a complete, receipt-verified Locklark
preparation artifact. Any unrelated file, partial pair, unreadable receipt, or
hash mismatch refuses the run. A ZIP and its receipt are written atomically
through a same-directory temporary file plus `os.replace`, with fsync before
publication; the receipt is published last.

## Reproducibility and receipt

The ZIP is deliberately simple and reproducible:

- entries are written in the fixed order shown above;
- every entry has the ZIP minimum timestamp `1980-01-01 00:00:00`;
- every entry is a regular file with Unix mode `0644`;
- compression is `ZIP_STORED`, avoiding compressor-version differences;
- the manifest is generated by `browser-extension/build.js`, not hand-edited;
- the public receipt is deterministic JSON (sorted keys, no wall-clock time,
  absolute path, user name, environment value, or secret).

The receipt records the ZIP name, size and SHA256; each entry name, size and
SHA256; generated manifest name/version/permissions/host permissions and browser
identity; the generator path and SHA256; and the exact build argv/cwd relative to
the repository. It is public metadata, not a signature. Verify a prepared ZIP
with, for example:

```sh
sha256sum /absolute/release-parent/locklark-browser-extension-chromium-unsigned.zip
unzip -l /absolute/release-parent/locklark-browser-extension-chromium-unsigned.zip
```

Two independent runs from identical repository content produce identical ZIP
bytes and identical receipt bytes. Tests cover this, the exact entry allowlist,
fixed timestamps/modes, symlink and unexpected-file refusal, permission and
identity refusal, output safety, no shell use, and no home/environment discovery:

```sh
python3 scripts/test_package_browser_extension.py
```

## Manifest and permission review

The generated manifest is validated against the product contract in
`scripts/package_browser_extension.py`. Anything outside the expected
top-level fields, permission set, HTTPS host permission, content-script
world/frame policy, action/options/commands, background shape, CSP, extension
version, or browser identity is refused. This includes additional or optional
permissions, extra host patterns, a changed Chromium public key, a changed
Firefox add-on ID, a different WebAuthn world, and unexpected capabilities such
as `externally_connectable`.

### `activeTab`

`activeTab` supports the explicit extension action/command path against the
current tab. `background.js` uses the user-invoked tab context and rejects
invalid tab/window IDs before probing the document
(`browser-extension/background.js:860-905`). It is not used to browse arbitrary
tabs in the background.

### `scripting`

`scripting.executeScript` is used to verify the actual top document/frame and to
inject the existing product probe/fill functions; examples are at
`browser-extension/background.js:873-905` and the other `executeScript` call
sites in the same file. Targets are restricted to validated tab/frame IDs and
document identities.

### `nativeMessaging`

The worker connects only to the fixed native host name
`org.locklark.browser` through `runtime.connectNative` at
`browser-extension/background.js:1030-1035`. The host name constant is
`internal/browserhost/protocol.go:24`. There is no localhost HTTP proxy. Vault unlock factors, private keys and TOTP seeds stay in the native process.
After explicit authorization, the selected username/password or short-lived OTP
necessarily passes through extension memory to fill the page; it is not saved
in extension storage. Public candidate lists are metadata projections.

### `storage`

`storage.local` holds extension preferences, per-origin UI/never-save settings,
and per-item automatic-login overrides. Examples:
`browser-extension/background.js:1721-1724`,
`browser-extension/background.js:2495-2499`,
`browser-extension/background.js:3783-3787`, and
`browser-extension/options.js:210-235`. It does not hold passwords, vault
factors, private keys, or TOTP values.

### `contextMenus` (Chromium/Edge only)

Chromium builds add `contextMenus` for the right-click vault menu
(`browser-extension/build.js:53-60`), using guarded `contextMenus` calls at
`browser-extension/background.js:641-665` and menu event registration around
line 819. Firefox builds deliberately omit this permission
(`browser-extension/build.js:56-59`), and the code treats the API as optional
(`browser-extension/background.js:647-658`), so Firefox has no right-click vault
menu in this package.

### `https://*/*` host access

Persistent HTTPS access is required for the in-page autofill UI and
document-start WebAuthn integration. The manifest uses only
`https://*/*` (`browser-extension/build.js:17-31`), never HTTP or `<all_urls>`.
The isolated content script refuses non-secure contexts, non-HTTPS pages, and
cross-origin frames (`browser-extension/content.js:1-26`). Firefox builds have
the same host/content-script set but no `contextMenus`.

### Isolated world versus `MAIN` world

- `core.js` + `content.js` run in the isolated extension world at
  `document_start`, with `all_frames: true`
  (`browser-extension/build.js:18-24`). The same-origin frame check in
  `browser-extension/content.js:5-26` means cross-origin frames stop before UI
  or credential handling.
- `webauthn.js` runs in the page's `MAIN` world at `document_start`, top frame
  only (`browser-extension/build.js:25-31`). It contains standard WebAuthn
  request/response data only and never vault keys or passwords
  (`browser-extension/webauthn.js:1-6`). The isolated bridge/native host
  authenticates the browser origin.

## No remote code or secrets in the store bundle

The bundle is the explicit local product file list above. The manifest CSP is
`script-src 'self'; object-src 'none'`
(`browser-extension/build.js:49-51`). HTML loads only local product scripts
(`browser-extension/popup.html:364-365`,
`browser-extension/options.html:231-232`). The packager additionally refuses a
source-map reference, remote HTML/CSS asset, non-allowlisted HTML script source,
`eval(...)`, or `new Function(...)` in product JavaScript. Vault factors, private keys and OTP seeds remain native. Authorized filled
values exist transiently in extension memory, so they must not be described as
never entering the extension. The distributable bundle contains code/assets,
not runtime credential values, signing keys, store credentials, vaults, profiles
or environment data.

## Store submission preparation

The same prepared ZIP can be started through each store flow, but **the signed
store package is a later artifact**:

- **Chrome Web Store:** upload the prepared Chromium ZIP through the release
  owner's Chrome Web Store item. For an existing published item, preserve its assigned identity and release
  ownership. For a first submission, verify the store-assigned public key/ID
  and reconcile the native allowlist before claiming installation support;
  this repository does not establish ownership of a published item. The manifest key
  fixes the development/unpacked ID to
  `geldnhjapnackobgknocomedmjgphnpe` (`browser-extension/build.js:7-8,53-55`;
  README note at `browser-extension/README.md:17-21`). That key is public
  identity metadata, not a release signature. Store-assigned identity must be
  verified against the native-host allowlist before local installation.
- **Microsoft Edge Addons:** use the Chromium ZIP. Edge registration is a
  separate store item/account flow; preserve the same package identity and
  verify the final Edge-assigned extension ID before registering the native
  host. Do not assume the Chrome Web Store item, review status, or signing
  result applies to Edge.
- **Firefox AMO:** upload the prepared Firefox ZIP to AMO for signing. The
  manifest fixes the add-on ID to `browser@locklark.local` and minimum Firefox
  `153.0` (`browser-extension/build.js:61-72`). AMO's signed XPI is the release
  artifact; the prepared ZIP here is unsigned. The manifest declares
  `data_collection_permissions.required = ["none"]`
  (`browser-extension/build.js:70`), which must remain accurate for the listing.

Store listing permissions justifications should use the actual reasons above,
not generic “security” claims. This repository does not provide or select a
privacy-policy URL, support URL, homepage, or license, and this preparation does
not create a signed release.

## Native-host installation and identity continuity

Build the native binaries separately, as documented in
`browser-extension/README.md:12-15`. Registration flags are declared in
`cmd/locklark-browser-register/main.go:12-16`:

```text
--browser       chrome, edge or firefox
--host          absolute path to the matching native binary
--output        absolute manifest path ending in org.locklark.browser.json;
                defaults to the browser's per-user NativeMessagingHosts directory
--register-user Windows only: register in HKCU; never elevates
--replace       explicitly replace an existing manifest/registration
```

Typical per-user registration (absolute paths required):

```sh
/absolute/path/locklark-browser-register \
  --browser chrome \
  --host /absolute/path/locklark-browser-chromium
/absolute/path/locklark-browser-register \
  --browser edge \
  --host /absolute/path/locklark-browser-chromium
/absolute/path/locklark-browser-register \
  --browser firefox \
  --host /absolute/path/locklark-browser-firefox
```

Use `--output /absolute/directory/org.locklark.browser.json` for an isolated
profile/manifest location. Registration refuses overwrite unless `--replace` is
explicit, rejects final symlinks/reparse points, and checks executable/manifest
ownership and write permissions; see
`internal/browserhost/manifest.go:51-69` and
`browser-extension/README.md:23-53`. On Windows, add `--register-user` and use
absolute `.exe` paths. Native messaging registration does not sign the browser
extension or prove a store install.

The native host name is fixed as `org.locklark.browser`
(`internal/browserhost/protocol.go:24`). The registration manifest allows
exactly `chrome-extension://geldnhjapnackobgknocomedmjgphnpe/` for Chrome/Edge
and exactly `browser@locklark.local` for Firefox
(`internal/browserhost/protocol.go:24-26`,
`internal/browserhost/manifest.go:60-66`). If a store flow assigns a different
identity, that is a release blocker: do not change the extension identity,
permissions, or native-host allowlist to paper over it. Resolve the store item
and identity first.

For updates, preserve continuity:

- Chromium/Edge: same store item, same public key/extension ID, monotonically
  increased manifest version, and a native-host manifest that still names the
  same allowed origin.
- Firefox: same AMO add-on ID `browser@locklark.local`, increased version, and
  an AMO-signed XPI update.
- Native host: keep the host name `org.locklark.browser`; if the binary path
  changes, rerun registration with `--replace`. Updating the native binary does
  not itself change extension identity.
- The native vault must be unlocked and the connection and operation must
  satisfy their existing authorization rules. Shared-desktop connections and
  enabled quick fill do not require manual pairing on every operation; a
  store update grants no additional authority.

## Remaining validation (not performed here)

The following are explicitly pending and must not be reported as passed:

- real Chrome Web Store, Edge Addons, and Firefox AMO signing/submission,
  review, listing publication, and signed-artifact installation;
- real install and update testing from each store-signed package, including
  extension-ID and version continuity across an update;
- local native-host registration and end-to-end native messaging on real
  Windows, macOS, and Linux browser profiles (including Edge and Firefox) after
  identity verification;
- real hardware security-key/passkey, screen-reader, OS accessibility, and
  browser permission-prompt validation;
- any support/privacy/license selection or store listing content.

This worktree only prepared and inspected unsigned ZIPs and their public
receipts.

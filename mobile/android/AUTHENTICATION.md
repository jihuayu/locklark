# Android per-operation authentication ordering

The device capsule key remains AES-256/GCM in AndroidKeyStore with user authentication required, timeout zero, and `AUTH_BIOMETRIC_STRONG | AUTH_DEVICE_CREDENTIAL`. Each encryption/decryption uses its own `BiometricPrompt.CryptoObject`. Background/lock cancels it; this change adds no lifecycle exemption or authentication cache.

The operation order is: initialize the cipher, request real OS authentication, require the same authenticated cipher and current lifecycle, feed the unchanged path/slot-bound AAD, then `doFinal`. Recheck current lifecycle before returning bytes; cancellation wipes the returned buffer.

This order is required by the Android 15 implementation at immutable release tag `android-15.0.0_r1`:

- [`AndroidKeyStoreAuthenticatedAESCipherSpi.java`](https://android.googlesource.com/platform/frameworks/base/+/android-15.0.0_r1/keystore/java/android/security/keystore2/AndroidKeyStoreAuthenticatedAESCipherSpi.java): `createAdditionalAuthenticationDataStreamer` uses chunk threshold zero; `AdditionalAuthenticationDataStream.update` calls `KeyStoreOperation.updateAad` immediately.
- [`AndroidKeyStoreCipherSpiBase.java`](https://android.googlesource.com/platform/frameworks/base/+/android-15.0.0_r1/keystore/java/android/security/keystore2/AndroidKeyStoreCipherSpiBase.java): `engineUpdateAAD` invokes that streamer and caches a Keystore failure for later cipher completion.
- [`BiometricPrompt.java`](https://android.googlesource.com/platform/frameworks/base/+/android-15.0.0_r1/core/java/android/hardware/biometrics/BiometricPrompt.java): the crypto object binds authentication to its Keystore operation; API 30+ permits device credentials with strong-biometric crypto policy.

The earlier app fed AAD before authentication on both storage paths. The thirteenth CI run proved secure lock-screen capability and successful owned PIN setup, then observed a generic enable refusal without an OS credential marker. It did not preserve enough detail to establish that AAD was the sole cause of that run's refusal. The ordering defect is fixed independently; the next real emulator OS prompt gate must establish the actual outcome.

Diagnostics contain only fixed stage, failure, allowlisted exception category and allowlisted OS error category. A process-local attempt counter and app PID bind them to the initiated action. The host harness records a floor before the UI tap, accepts only a subsequent begin/failure pair for the same live PID and newest attempt, and never prints arbitrary exception text, paths, key aliases, capsules, factors, or OS error strings. The Go boundary continues to normalize storage failures; the Kotlin callback retains only its own attempt's fixed classification for native reporting.

JVM ordering/cancellation tests and Android compilation cannot prove successful OS authentication or physical hardware protection. The native gate must perform real PIN enrollment, capsule encryption/decryption, cancellation, and fresh unauthenticated-key refusal. Its reported Keystore security level is evidence about the emulator, not a physical device claim.

## Prompt observer ownership

The fourteenth CI run reached `DEVICE_WAIT` / `TIMEOUT` with no OS callback error. This does not establish that the OS prompt was absent: the observer queried only `dumpsys window windows` and assumed the SystemUI owner UID was 1000. At `android-15.0.0_r1`, [`WindowManagerService.java`](https://android.googlesource.com/platform/frameworks/base/+/android-15.0.0_r1/services/core/java/com/android/server/wm/WindowManagerService.java) handles `windows` by dumping WindowState records without the DisplayContent focus section; [`DisplayContent.java`](https://android.googlesource.com/platform/frameworks/base/+/android-15.0.0_r1/services/core/java/com/android/server/wm/DisplayContent.java) prints `mCurrentFocus`. [`SystemUI/AndroidManifest.xml`](https://android.googlesource.com/platform/frameworks/base/+/android-15.0.0_r1/packages/SystemUI/AndroidManifest.xml) declares `android.uid.systemui`, so a fixed system-server UID is insufficient evidence of SystemUI ownership.

The harness now reads the full window dump. It resolves exact SystemUI/Settings package UIDs with `pm list packages -s -U`, requiring one exact installed-system-package record; the app UID is resolved only after the APK matches the owned fixture. After reinstall it resolves identities again. A unique focused Window token must match one WindowState record whose authoritative owner UID and package both match this verified mapping. A title resembling a trusted component is insufficient. PIN entry still requires enabled, bounded real credential controls in that same verified OS package. Missing, ambiguous or mismatched evidence fails closed; unrelated system windows are not authentication prompts.

Failure metadata contains only fixed booleans and candidate-package enums for focus presence, matching WindowState presence, verified owner/package, known OS UID, and credential-resource markers. It does not include arbitrary titles, packages, UIDs or window dumps in public output. No application lifecycle behavior or authentication timeout changes as part of this observer correction; the next real OS gate must determine whether the valid prompt can be completed.

The PIN driver brackets every fresh hierarchy with two full focus observations. The private Window token, owner UID and package must match before and after; immediately before every PIN key or text action, another such observation must still match the selected credential window and contain one enabled, visible, on-screen exact OS control. Duplicate inputs/keys, failed queries or changed windows prevent PIN input. A single explicit “Use PIN” transition may select a new credential window; it does not restart authentication, reset the deadline or retry PIN entry. Final Enter additionally requires the original input mode: the same unique focused entry resource/control, or the same complete set of ten unique keypad controls. A changed window, fallback-only view or different input mode receives no final Enter; subsequent app-state checks determine whether OS authentication completed.

Visibility follows the actual API 35 XML contract rather than requiring an absent attribute: [`DumpCommand.java`](https://android.googlesource.com/platform/frameworks/base/+/android-15.0.0_r1/cmds/uiautomator/cmds/uiautomator/src/com/android/commands/uiautomator/DumpCommand.java) uses `getRootInActiveWindow` by default; [`AccessibilityNodeInfoDumper.java`](https://android.googlesource.com/platform/frameworks/base/+/android-15.0.0_r1/cmds/uiautomator/library/core-src/com/android/uiautomator/core/AccessibilityNodeInfoDumper.java) skips children whose `isVisibleToUser()` is false and serializes `focused` but no `visible-to-user` attribute. [`AccessibilityNodeInfoHelper.java`](https://android.googlesource.com/platform/frameworks/base/+/android-15.0.0_r1/cmds/uiautomator/library/core-src/com/android/uiautomator/core/AccessibilityNodeInfoHelper.java) clips node bounds to the display. The driver accepts this missing visibility attribute, rejects explicit false/unknown values, and independently requires nonempty bounds wholly on screen. These observations guard the controlled emulator driver; they do not make separate ADB observation and input commands an atomic OS transaction.
